# stroi-mods

Публичный репозиторий модификаций («модов») для приложения [stroi.homes](https://stroi.homes).
Моды из этого репозитория вшиваются в приложение на этапе сборки (build-time
vendoring) — они не загружаются рантаймом с бэкенда.

## Формат мода

Каждый мод — это директория `mods/<slug>/` со следующей структурой:

```
mods/<slug>/
  stroi-mod.json     # манифест мода (схема ниже)
  declaration.json    # обязателен при runtime: "declarative"
  fixtures/            # тестовые фикстуры для валидации/разработки
  README.md            # описание мода для пользователя
```

Манифест `stroi-mod.json` описывает мод: идентификатор (совпадает с именем
директории), версию, `runtime` (`declarative` — декларативный HTTP/notify-флоу
без исполняемого кода, либо `sandboxed-js` — код, исполняемый в песочнице
хоста), триггер события, разрешения (`permissions`), категорию, теги и
пользовательские поля ввода (`inputs`). Формат манифеста определён спекой
основного репозитория (Stage 4A, `docs/superpowers/specs/2026-07-10-modifications-stage-4a-publish-moderation-design.md`
в `aquahitt/stroi-homes`). Сам процесс build-time вендоринга модов в приложение
описан в `docs/superpowers/specs/2026-08-13-mods-buildtime-vendoring-design.md`
того же репозитория.

## Валидатор схемы (вендоренная копия)

`scripts/manifest-schema.ts` и `scripts/validate.ts` в этом репозитории —
**вендоренная копия** валидатора манифестов из основного (приватного)
репозитория `packages/mod-cli/src/manifest-schema.ts`. Она вендорится, а не
подключается через checkout платформы в CI, потому что основной репозиторий
приватный, а PR в этот репозиторий приходят из форков внешних авторов —
GitHub по дизайну не передаёт секреты форкам, так что checkout платформы по
токену не сработал бы для основного сценария (внешний контрибьютор шлёт PR).

Расхождение (drift) между этой копией и актуальной схемой платформы не
критично: при подключении мода в сборку приложения платформа повторно
валидирует каждый манифест на своей стороне (`sync-mods`), так что устаревшая
локальная копия может максимум пропустить в PR то, что позже будет отклонено
на сборке — но не наоборот.

В будущем эта копия будет заменена импортом схемы из опубликованного в npm
пакета `@stroi/mod-cli`, когда платформенная команда его выпустит.

## Процесс публикации мода

1. Форкните репозиторий, добавьте директорию `mods/<slug>/` со своим модом.
2. Откройте Pull Request в `main`.
3. CI (`.github/workflows/validate.yml`) прогоняет валидатор по всем модам в
   репозитории — PR не может быть смёржен, если валидация красная.
4. Ревью PR владельцами репозитория (см. `CODEOWNERS`) — это модерация мода.
5. После merge в `main` мод **не деплоится автоматически**. Он попадает в
   приложение только со следующим релизом stroi.homes, когда основной
   репозиторий обновит зафиксированный commit SHA этого репозитория
   (`mods.lock.json`) и повторно провалидирует моды на своей стороне.

## Слаги модов

Слаги директорий (`mods/<slug>/`) — это стабильные идентификаторы, под
которыми в проде живут установки и отзывы пользователей. Слаги **нельзя**
переименовывать после публикации.

Текущие моды:

- `mods/notify-registration/` — уведомление об открытии регистрации у
  застройщика.
- `mods/ghb-autoregister/` — автоматическая регистрация на объекты ГЖБ
  (только Android).
